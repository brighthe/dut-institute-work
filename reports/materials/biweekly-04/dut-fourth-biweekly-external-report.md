## 会议议程

1. 汇报本周期数学结构梳理、多后端原型验证和异构并行架构规划的阶段成果。
2. 说明 TensorFem 当前已经验证的能力、正确性结果和性能边界。
3. 讨论新计算路线与 SGSim 原有流程的关系，以及 `DBManager`、分区和结果衔接接口。
4. 确认 9 月底前的验证范围、协作输入和方案评审口径。

## 1. 本周期总体进展

本周期围绕“异构并行验证 Demo、算例数学结构分析、异构并行研发方案”完成了一次初步闭环：

- 形成四节点 Reissner-Mindlin 壳单元线性静力分析文档，用统一的张量语言描述几何、运动学、单元离散、载荷、约束、总体方程和结果恢复；
- 建立 TensorFem 异构并行验证 Demo，完成 `xtensor CPU`、`Torch CPU` 和 `Torch CUDA` 三种后端的运行时切换，并验证活动数据库服务和独立 `.db` 文件两种数据入口；
- 在中型 CTETRA4 算例上完成 24 次正式求解，三种后端、两种数据入口的位移、反力和应力均与 SGSim CPardiso 基准保持约 `10^-12` 量级的相对差异；
- 形成多后端异构并行初步方案，明确保留 SGSim 原有 CPU/MPI 路线，并通过 `DBManager` 建设独立新计算路线。

当前成果证明了有限元数据接入、多后端切换和结果对照的技术可行性，但尚不代表已经实现多 rank、全 GPU 求解或生产级性能加速。

## 2. 本周期工作进展

### 2.1 异构并行验证 Demo：TensorFem 数据接入、后端运行与性能验证

**做了什么**

- 建立 TensorFem 异构并行验证 Demo，支持从 SGSim 当前活动的 `DBServiceFactorySP` 直接取数，也支持独立读取 `.db` 文件。
- 将数据入口与计算后端解耦：两种入口从 `Model` 之后共用 `Prepare`、后端计算、PETSc 求解和结果恢复逻辑。
- 在同一构建产物中接入 `xtensor CPU`、`Torch CPU` 和 `Torch CUDA`，可通过命令行在运行时切换，无需重新编译。
- 固化本轮编译依赖、后端选择、求解容差和运行命令，并完成四项单元测试。

**运行闭环**

- SGSim 直接法、SGSim 迭代法、TensorFem Service 三种后端和 TensorFem 独立 `.db` 三种后端均完成真实 TET 算例求解。
- 两种数据入口在进入 `Prepare` 后的计算行为基本一致；Service 路径避免重复读取数据库文件和附加校验，数据入口更短。
- 简化了求解参数接口：CG、Jacobi 和最大迭代次数由程序提供默认值，调用方只需设置相对和绝对收敛容差。

**验证条件与性能结果**

- 算例规模：18,081 个节点、96,000 个 CTETRA4 单元；
- 运行规模：单 MPI 进程，`OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`；
- 每条路径重复运行 3 次，共完成 24 次正式求解，全部正常结束；
- 以 SGSim CPardiso 直接法结果作为本轮对照基准。

**正确性结果**

- SGSim 迭代法相对直接法的位移、反力和应力相对 L2 差异均处于 `10^-13` 量级。
- TensorFem 三种后端在两种数据入口下的位移、反力和应力相对 L2 差异均处于 `10^-12` 至 `10^-13` 量级。
- Service 与独立 `.db` 的 Torch CPU 复测均为 556 次 KSP 迭代，残差范数约 `2.28e-17`，两条入口的位移、反力和应力逐值一致。

**阶段性能观测**

| 路径 | 平均墙钟时间 |
| --- | ---: |
| SGSim CPardiso 直接法 | `5.823 s` |
| SGSim TPetscKsp CG/Jacobi | `5.992 s` |
| Service + xtensor CPU | `7.336 s` |
| Service + Torch CPU | `6.074 s` |
| Service + Torch CUDA | `6.186 s` |
| 独立 `.db` + xtensor CPU | `8.148 s` |
| 独立 `.db` + Torch CPU | `6.935 s` |
| 独立 `.db` + Torch CUDA | `7.050 s` |

**当前结论与边界**

- 已验证“同一有限元计算流程、多种张量后端、两种数据入口”的工程闭环。
- 本轮相同环境中 SGSim 直接法平均最快；TensorFem 中 Torch CPU 快于 xtensor CPU。
- Torch CUDA 与 Torch CPU 接近但未形成加速，主要原因之一是线性求解仍在 CPU，当前算例规模和数据传输成本也不足以证明 GPU 收益。
- Service 与独立 `.db` 的主要时间差来自文件读取、两次全文件 SHA-256 和独立参考结果比较，后续计算阶段耗时接近。
- 当前仅验证单进程、`SOL 101`、CTETRA4、MAT1、PSOLID、PLOAD4、SPC 平移约束和基本坐标系；尚未证明复杂单元、复杂约束或 MPI 分布式路径可用。
- 当前 `Torch CUDA` 只覆盖 TensorFem 张量计算，PETSc 矩阵、向量和 CG/Jacobi 仍在 CPU，不能表述为全 GPU 求解。
- 本轮数据只用于验证当前单进程中型 TET 算例，不能外推到多 rank、大规模模型或复杂约束场景；当前也未把内存作为验收指标。

详细材料：[TensorFem 多后端验证](tensorfem-multi-backend-validation.md)

### 2.2 针对大工方算例的数学结构推导与分析

本项工作不是独立的理论整理，而是从大工方提供的算例出发，建立有限元计算的统一数学和张量表达，为后续异构并行、批量张量计算、`matrix-free`、网格分区和预条件器设计提供依据。

**做了什么**

- 系统梳理四节点 Reissner-Mindlin 壳单元的中面几何、运动学、膜/弯曲/横向剪切应变和截面本构。
- 给出非协调膜应变、MITC4 横向剪切、内部变量静态凝聚、钻转稳定化、偏置和节点坐标变换的离散表达。
- 将载荷、SPC/MPC 类线性运动约束、约束消元、总体方程、反力和结果恢复组织为完整映射链。
- 明确约束处理与 BDDC、FETI-DP、重叠 Schwarz 等区域分解方法之间的逻辑顺序。

**形成的价值**

- 建立了从连续力学、单元离散到代数系统的统一张量表达，可作为后续批量单元计算、`matrix-free` 算子和分区策略的数学输入。
- 明确多点约束会改变约化系统的耦合图；分区、局部矩阵提取和粗空间构造必须包含这些跨子域耦合。

**当前边界**

- 当前成果是理论和离散设计文档，尚未完成与 SGSim 壳单元实现的逐项源码映射、数值回归和性能验证。
- 文档当前聚焦四节点壳单元，不代表已经覆盖 SGSim 全部单元、材料、载荷和分析类型。

详细材料：[壳结构线性静力分析](reissner-mindlin-shell-linear-static.md)

### 2.3 异构并行研发初步方案

**形成的初步方案**

- 保留 SGSim 原有 CPU/MPI 计算流程作为稳定兼容路线和结果基准。
- 新路线通过 `DBManager` 获取网格、材料、载荷、边界、自由度、约束和分区数据，独立建设有限元计算内核，不直接复用原有单元计算、全局装配和求解调用链。
- 新内核优先采用 `Operator::apply(x,y)` 形式的 `matrix-free` 算子，同时保留预条件子、部分组装、局部缓存和受控显式矩阵适配能力。
- 先完成 CPU 参考闭环，再接入 NVIDIA CUDA；MPI 负责跨 rank 交换、同步和归约，设备后端负责 rank 内局部计算。
- 通过后端注册、能力查询、执行上下文和内存/缓存管理，逐步形成 CPU/CUDA 可选择的运行机制。

**当前结论与边界**

- 已明确原有路线与新路线并存、数据接入与计算内核解耦、CPU 先行再扩展 CUDA/MPI 的实施顺序。
- `matrix-free` 是新路线的优先组织方式，但并不天然保证收敛、内存下降或端到端加速；仍需针对不同问题验证预条件器、通信和数据传输成本。
- 当前文档属于研发规划和候选架构，不表示四层架构、分布式对象、多 GPU 或多节点能力已经全部实现。

**待进一步讨论和确认**

- `DBManager` 能够向新路线稳定提供的数据范围、批量访问方式和并发访问约束；
- 新路线的结果组织、导出方式及其与 SGSim 现有结果管理流程的衔接边界；
- 首期必须覆盖的单元、材料、载荷、约束、后端和代表性算例；
- CPU/CUDA、多 rank、多 GPU 和多节点验证的阶段顺序、目标环境与验收指标。

详细材料：[HPC 研发规划](rd-plan-heterogeneous-sections-final.md)

## 4. 待讨论与待协助事项

本节围绕双方在外部群中已提出的问题和初步回复展开，会议重点是进一步确认技术处理方式、协作边界和实施节奏。

### 4.1 `DBManager` 数据到显存的搬运风险

**大工方关注**

以 `DBManager` 作为当前切入点较为直观，也符合此前 MPI 改造方式；但数据库中的数据，特别是不连续数据，搬运到显存时可能产生较大开销，成为异构计算的性能隐患。

**我方当前理解与处理思路**

- `DBManager` 在当前 Demo 中主要承担便利的数据接口和与原有计算流程对照的起点，不应成为新计算内核长期绑定的数据结构。
- 新架构将在 `DBManager` 与计算内核之间设置独立的数据适配与连续张量组织层，使后端计算不直接依赖数据库内部布局。
- 后续可分别优化 `DBManager` 的批量读取和预取，也可以在保持上层计算接口稳定的情况下重构或替换数据入口。
- 性能评估需要单独统计数据库读取、数据整理、主机到设备传输、设备计算和结果回传，避免只依据 GPU Kernel 时间判断收益。

**会议需要进一步确认**

- `DBManager` 可提供的批量读取、连续数据视图、预取和并发访问能力；
- 哪些数据适合一次性预存，哪些数据需要按批次或按需传输；
- 新路线结果采用独立组织和导出，还是需要与现有结果管理流程衔接。

### 4.2 复杂约束与 ghost 数据交互

**大工方关注**

现有代码包含较多约束单元处理，约束关系可能跨越分区，ghost 数据的组织和交互会比较复杂，预计是后续分布式异构计算的主要难点之一。

**我方当前理解与处理思路**

- 网格分区不能只考虑网格拓扑和几何位置，还需要考虑 RBE、MPC 等约束关系及不同单元的计算工作量。
- 多点约束会改变约化代数系统的耦合图；如果一个约束跨越多个子域，分区、局部矩阵提取、粗空间构造和 ghost 交换都必须保留这种耦合。
- 架构上需要明确 owned/ghost 自由度、约束所有权、共享贡献归约和结果恢复规则；算法上需要探索兼顾拓扑、约束、计算负载和通信成本的分区策略。
- 当前单进程 TensorFem Demo 尚未覆盖这一问题，后续应先建立多 rank 的最小约束算例，再逐步扩展到复杂工程算例。

**会议需要进一步确认**

- SGSim 当前约束处理、分区、局部—全局映射及 ghost 数据的正式语义和可用接口；
- 首期优先支持和验证的约束类型、典型算例及正确性判据；
- 网格分区优化由双方如何分工，以及分区结果如何交给新计算路线使用。

### 4.3 架构实现工作量与时间规划

**大工方关注**

有限元新内核、抽象层接口和 CUDA 后端与现有代码的设计差异较大，改造工作量可能超出当前估计。现有规划中部分节点安排在次年 3 月和 6 月，需要评估是否给予更充分的设计、实现和验证时间。

**我方当前理解与处理思路**

- 认可新内核、抽象接口和 CUDA 后端的工作量较大，需要为数学校核、接口设计、CPU 参考实现、CUDA 实现、分布式验证和回归测试留出充足时间。
- 后续计划应区分“架构实现”和“具体功能实现”：前者先稳定数据、算子、执行、内存和通信契约，后者按单元、材料、载荷、约束和后端拆分，使双方可以并行开发。
- 建议采用分阶段交付：先形成限定算例的 CPU 正确性闭环和稳定接口，再完成单节点 CUDA，随后推进多 rank、多 GPU 和更多功能覆盖。
- 每个阶段分别验收接口、正确性、性能和适用边界，不用单个 Demo 可运行替代完整架构和功能验收。

**会议需要进一步确认**

- 次年 3 月、6 月节点分别对应架构设计、框架实现、限定功能闭环还是完整功能覆盖；
- 是否根据实际工作量调整里程碑，为基础架构、CUDA 后端和分布式验证增加时间；
- 双方可以并行承担的功能模块、接口交付物、代码协作方式和阶段验收标准。
