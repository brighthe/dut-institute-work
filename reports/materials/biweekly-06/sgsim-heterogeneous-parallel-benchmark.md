# SGSim × TensorFem · 多卡与多线程性能评估

## 原始文件

- 原件：[SGSim_异构并行性能测试.html](SGSim_异构并行性能测试.html)

## 核心内容与结论

1. **本次进展与比较口径修正**（第 1–3 页）
   - 补齐单机多卡运行与 CPU 三路径（`CPU 基线` SGSim 迭代法、`CPU-xtensor`、`CPU-Torch`）的多进程 $\times$ 多线程（1 / 2 / 4 / 8 线程）组合测试。
   - 新增 `400w` 规模算例数据：覆盖 `100w-hex`、`100w-tet`（进程数 1 / 2 / 4 / 8，线程 1 / 2 / 4 / 8，其中 8 线程含 1 / 2 / 4 进程）、`400w-hex`（进程数 4 / 6 / 8，线程 1 / 2 / 4）与 `400w-tet`（进程数 6 / 8，线程 1 / 2 / 4）。
   - **统计与对照口径修正**：CPU 张量后端与 CPU 基线严格按**同算例、同进程数、同 CPU 线程数**横向比较；CPU 三路径的完整求解时间由 100 步 KSP 计时按目标收敛步数外推得到（标为「预测」），`GPU-Torch` 路径为完整收敛运行（标为「实测」）；将总时间扣减组装与 KSP 迭代后的残余项定义为「准备/其他」（含 I/O、数据整理与输出等），避免将残余开销全部归因于通信。
2. **运行环境与上次数据异常说明**（第 4 页）
   - **硬件环境（Host）**：双路 Intel Xeon Gold 6354（36 物理核 / 72 逻辑核，$3.00\text{ GHz}$，2 个 NUMA 节点，每节点挂载 4 张 GPU）；宿主机内存 $314\text{ GiB}$（容器上限 $280\text{ GiB}$）；$8 \times \text{NVIDIA A10}$ GPU（单卡 $23,028\text{ MiB} \approx 22.5\text{ GiB}$，功耗上限 $150\text{ W}$）。
   - **软件环境（Container）**：Ubuntu 22.04.2 LTS，GCC/G++ 11.4.0，CMake 3.22.1，Intel MPI 2021.14，CUDA Toolkit 12.6（`nvcc V12.6.85`），PETSc 3.22.1（复数双精度、64 位索引，开启 `--with-cuda` 与 `--with-openmp`），Intel oneAPI MKL 2025.0.1（`libmkl_intel_thread + libiomp5`）。
   - **上次数据异常根因**：环境中同时存在 GNU `libgomp`（GCC OpenMP 运行库）与 Intel `libiomp5`（MKL 线程运行库）两套 OpenMP 运行库混用，引发线程资源竞争与切换开销，导致上次汇报中 SGSim 原生迭代法耗时偏高。
3. **端到端总时间对比与扩展趋势**（第 5 页及内嵌数据集）
   - **总体收益**：在全部已有同算例、同进程、同线程对照配置下，相对 CPU 基线（SGSim 迭代法），CPU 张量后端总时间降低约 **$0.7\%\text{–}43.5\%$**（`CPU-xtensor` 降低 $0.7\%\text{–}19.8\%$，`CPU-Torch` 降低 $3.5\%\text{–}43.5\%$）；`GPU-Torch` 相对同算例、同进程数的 CPU 基线降低约 **$28.0\%\text{–}87.9\%$**。
   - 代表性配置下的端到端总时间（单位：$\text{s}$，CPU 为外推预测，GPU 为收敛实测）：

   | 算例（KSP 步数） | 进程数 `np` | CPU 线程 = 1（基线 / xtensor / Torch） | CPU 线程 = 4（基线 / xtensor / Torch） | GPU-Torch（实测） |
   | --- | --- | --- | --- | --- |
   | **100w-hex**（586–587 步） | 1 | 270.45 / 268.64 / 244.09 | 130.53 / 125.77 / 77.92 | **32.65** |
   | **100w-hex**（586–587 步） | 4 | 89.42 / 84.11 / 79.24 | 55.04 / 49.73 / 39.35 | **25.62** |
   | **100w-hex**（586–587 步） | 8 | 55.69 / 53.10 / 50.93 | 41.27 / 39.62 / 35.30 | **25.31** |
   | **100w-tet**（1,485 步） | 1 | 309.55 / 296.19 / 283.12 | 160.72 / 137.59 / 125.81 | **52.90** |
   | **100w-tet**（1,485 步） | 4 | 121.93 / 113.63 / 110.10 | 99.52 / 79.80 / 75.54 | **53.72** |
   | **100w-tet**（1,485 步） | 8 | 88.57 / 81.91 / 80.46 | 78.05 / 72.81 / 75.34 | **54.11** |
   | **400w-hex**（922–925 步） | 4 | 368.67 / 346.77 / 322.19 | 258.22 / 232.99 / 191.87 | **94.77** |
   | **400w-hex**（922–925 步） | 6 | 270.23 / 255.30 / 246.11 | 195.72 / 172.77 / 152.09 | **84.41** |
   | **400w-hex**（922–925 步） | 8 | 226.20 / 210.36 / 202.80 | 165.45 / 154.50 / 132.45 | **79.80** |
   | **400w-tet**（2,329 步） | 6 | 444.74 / 423.25 / 411.63 | 429.47 / 391.94 / 383.70 | **201.89**（1 线程，单次） |
   | **400w-tet**（2,329 步） | 8 | 385.98 / 365.88 / 359.79 | 308.39 / 278.02 / 275.56 | **192.97**（1 线程，三次均值） |

   - **扩展性结论**：
     - **CPU 扩展**：四个算例随进程数增加均缩短总时间；增加 OpenMP/MKL 线程总体有效，但存在收益递减甚至回退（例如 `100w-tet` 在 `np=1` 下 4 线程 `CPU-Torch` 为 $125.81\text{ s}$，8 线程回退至 $145.32\text{ s}$），线程数并非越多越好。
     - **GPU 扩展**：`100w-hex` 从 $32.65\text{ s}$（`np=1`）降至 $25.31\text{ s}$（`np=8`），`400w-hex` 从 $94.77\text{ s}$（`np=4`）降至 $79.80\text{ s}$（`np=8`），后期收益趋缓；`400w-tet` 从 $201.89\text{ s}$（`np=6`）降至 $192.97\text{ s}$（`np=8`）；`100w-tet` 在 $52.90\text{–}57.44\text{ s}$ 之间波动。GPU 在全部已有对照配置中更快，但 CPU 增强多进程/多线程并行后两者差距收窄。
4. **分阶段（数据准备/其他、组装、求解）时间分析**（第 6 页及内嵌数据集）
   - 8 进程（`np=8`，CPU 线程 $= 1$）下四算例的阶段耗时拆分（单位：$\text{s}$）：

   | 算例（`np=8`） | 阶段 | CPU 基线 | CPU-xtensor | CPU-Torch | GPU-Torch（实测） |
   | --- | --- | --- | --- | --- | --- |
   | **100w-hex** | 准备/其他 / 组装 / 求解 | $\approx 19.99$ / $\approx 10.00$ / $25.71$ | $14.53$ / $12.91$ / $25.66$ | $14.54$ / $10.63$ / $25.76$ | $19.15$ / $5.55$ / **$0.61$** |
   | **100w-tet** | 准备/其他 / 组装 / 求解 | $\approx 43.35$ / $\approx 11.00$ / $34.21$ | $38.69$ / $9.27$ / $33.95$ | $38.67$ / $7.62$ / $34.17$ | $46.17$ / $6.93$ / **$1.01$** |
   | **400w-hex** | 准备/其他 / 组装 / 求解 | $\approx 70.89$ / $\approx 41.00$ / $114.31$ | $46.73$ / $50.42$ / $113.21$ | $45.47$ / $43.03$ / $114.30$ | $54.95$ / $21.65$ / **$3.21$** |
   | **400w-tet** | 准备/其他 / 组装 / 求解 | $\approx 159.40$ / $\approx 47.00$ / $179.58$ | $140.66$ / $41.43$ / $183.79$ | $139.72$ / $35.66$ / $184.42$ | $158.60$ / $29.41$ / **$4.96$** |

   - **阶段瓶颈结论**：
     - **计算显著缩短**：GPU 的组装与求解时间均随进程数增加而持续下降；相对同算例、同进程的单线程 CPU 基线，**GPU 求解阶段耗时降低约 $97.0\%\text{–}97.7\%$**。
     - **准备阶段成为多卡主要瓶颈**：GPU 的「准备/其他」时间随进程数增加而增长，在 8 进程时占 GPU 端到端总时间的 **$76\%$（`100w-hex`）/ $85\%$（`100w-tet`）/ $69\%$（`400w-hex`）/ $82\%$（`400w-tet`）**，抵消了部分设备端计算收益。
     - **CPU 收益来源**：单线程下 CPU 张量后端的 KSP 求解耗时与基线接近，总时间收益主要来自数据准备与组装阶段（但 Hex 算例上 `xtensor` 组装仍慢于基线）。
5. **未来展望与后续实施方向**（第 7 页）
   - **适配 SGSim，重构张量计算后端**：完善 SGSim 数据与求解流程接入，梳理后端接口与数据生命周期，统一 CPU / GPU 路径，降低重复转换与维护成本。
   - **优化 GPU 通信与数据流转**：细分 MPI 通信、主机—设备传输与同步计时，减少冗余数据交换和等待，探索通信与计算重叠以改善多卡扩展效率。
   - **优化 Tet / Hex 算子，为 Matrix-free 做准备**：围绕基函数、积分与局部算子优化数据布局和批处理，逐步验证算子直接作用于向量的实现。
   - **评估跨节点多卡扩展**：从单机多卡推进到多机多卡，评估跨节点通信开销与负载均衡，验证更大规模算例下的并行效率。
