# 《HPC 研发规划（2026-2027）》多后端异构并行部分

## 1.3.2 多后端异构并行计算

**架构说明：** 参考 MFEM 的算子分解、后端可插拔和运行时选择思想，面向大规模有限元计算构建由业务层、抽象层、实现层和基础设施层组成的多后端异构并行架构。业务层负责表达线性代数与分布式数据对象、网格与分区、函数空间与自由度、弱形式与有限元算子以及求解器与迭代控制；抽象层通过算子与 Kernel、分布式张量与数据交换、执行与内存运行时、后端注册与能力查询等统一契约，解耦有限元算法与具体硬件、编程模型和通信实现；实现层提供 X86/ARM CPU 后端和 NVIDIA CUDA 后端，OpenMP、线程池等作为 CPU 后端内部的并行实现方式，其他 GPU 或加速器通过 HIP、SYCL 或厂商接口按需接入，第三方 Kernel 和数值库通过适配器按算子和后端使用；基础设施层由 MPI 通信运行时、硬件与设备环境以及工程保障组成，其中 MPI 负责跨 rank 数据交换、同步和归约，不负责网格分区、数据所有权确定或局部 Kernel 执行。

有限元计算以 `matrix-free` 算子为主路径，求解器通过统一的 `Operator::apply(x,y)` 接口调用算子作用。算子根据网格、函数空间、自由度映射、材料、边界条件和积分规则，完成局部自由度提取、几何映射、数值积分、局部贡献生成和全局贡献归约；分布式对象通过 `Ownership/Halo` 管理 owned/ghost 数据、邻居关系和跨 rank 交换。对于不同单元类型、材料模型和内存条件，可按需采用在线重算、部分组装、积分点数据缓存、`LocalBlock`、`ElementCache` 或受控显式矩阵适配器；对适用的张量积单元，可进一步采用 sum factorization 优化算子计算，但不将其固化为所有问题的统一实现。

运行时通过 `Backend Registry/Capability Query` 枚举后端和设备，并根据算子、单元、数据类型、布局及设备能力创建 `ExecutionContext`。`Memory/Cache Manager` 负责主机与设备数据的驻留、迁移、缓存、内存预算和同步；选定后端后，由对应 CPU 或 GPU Kernel 执行局部计算。MPI 根据分布式对象提供的通信契约完成 halo 交换、共享自由度贡献归约和全局集合通信；通信计算重叠、GPU 直接通信和拓扑感知优化作为预留或可选扩展。

**实施策略：** 在不改变 SGSim 现有 CPU/MPI 计算流程及其调用链的前提下，保留原有流程作为稳定的兼容路线和结果对照基线。新增路线仅通过 `DBManager` 获取网格、材料、载荷、边界、自由度、约束和分区等数据，经数据适配层完成索引转换、结构校验和连续张量组织后，进入独立的有限元计算流程。新路线不复用 SGSim 原有的单元计算、全局装配和求解调用链，而是独立构建分布式网格、函数空间、自由度映射、`matrix-free` 算子、张量数据和求解控制。实施时先完成新内核 CPU 参考后端和限定算例的正确性闭环，再接入 NVIDIA CUDA 后端，逐步验证主机/设备数据传输、局部 Kernel 执行、`Ownership/Halo` 数据交换、共享自由度贡献归约及多 rank 运行；其他 GPU 或加速器后端按照统一接口，根据实际需求和验证结果按需实现。通过独立数据适配、算子抽象、执行运行时和后端实现，形成与 SGSim 原有 CPU 流程并列的异构并行计算路线，并依据正确性、内存占用、通信开销和端到端性能验证结果，逐步推进后端扩展和工程化集成。

## 2.2 多后端异构并行计算

### 2.2.1 研发目标（能力、产品）

在不改变 SGSim 原有 CPU/MPI 计算路径及其调用链的前提下，依托 `DBManager` 的数据管理能力，增加一条独立的有限元多后端异构计算路线。新路线不直接复用 SGSim 原有的单元计算、全局装配和求解调用链，而是通过独立的数据适配层读取网格、材料、载荷、边界、自由度、约束和分区信息，构建新的有限元计算内核。SGSim 原有流程作为稳定的兼容路线和结果对照基线保留；本节所述四层架构是目标设计，2027 年计划按验证结果分阶段落地，并不表示所有目标模块在年初已经具备。

新内核在接口层支持以 `Operator::apply(x,y)` 为入口的 `matrix-free` 计算路径，并将其列为重点研发与验证方向。同时保留批量局部计算、受控显式组装和部分组装等路径，用于 CPU 参考、结果校核、预条件子构造、特定问题求解和必要时的回退。首期在限定单元和约束范围内，验证 `matrix-free` 算子作用与显式装配结果的一致性；是否将其扩展到复杂约束、BDDC 和大规模分布式求解，依据后续收敛、内存、通信和端到端性能测试结果确定。

新内核以本地张量、分布式向量与张量为主要数据对象，解耦有限元算法与具体设备及编程模型。首先完成 CPU 参考后端，再接入 NVIDIA CUDA；在新路线内部实现后端注册、能力查询和设备选择，其他 GPU 或加速器按实际需求和验证结果按需扩展。设备执行与分布式通信职责分开，MPI 专门负责 rank 间的数据交换、同步和归约。

本节目标包括：

1. 建立 `DBManager` 到新有限元内核的数据读取与适配契约，明确网格、材料、载荷、边界、自由度、约束和分区数据的组织方式，以及新路线的结果组织与导出方式；与现有结果管理流程的衔接按确认后的接口实施。
2. 建立算子与 Kernel、分布式张量与数据交换、执行与内存运行时、后端注册与能力查询等统一接口，支持 `matrix-free`、受控显式组装和部分组装等不同计算路径在统一契约下切换。
3. 完成限定单元、材料、载荷和约束组合内的 CPU/CUDA 可切换计算闭环，验证 `matrix-free` 算子作用、显式参考路径和结果恢复的一致性，并与 SGSim 原有 CPU 路径进行正确性对照。
4. 建立并验证分区网格、owned/ghost 数据、MPI 通信以及多 rank 与 GPU 绑定机制，为 `matrix-free` 算子执行、显式装配、预条件子构造和后续分布式异构计算提供统一的数据基础。
5. 形成具有验证证据、可按支持范围部署的异构并行框架、使用说明和适用边界，明确不同单元、约束、求解器、后端和硬件配置下的已验证能力、性能结论及限制。

### 2.2.2 实施计划（技术路线、现状、预期成果、里程碑、开发清单）

#### 2.2.2.1 技术路线

参考 MFEM 的算子分解、后端可插拔和运行时选择思想，总体设计采用业务层、抽象层、实现层和基础设施层。业务层负责表达线性代数与分布式对象、网格与分区、函数空间与自由度、弱形式与有限元算子、求解器与迭代控制；抽象层定义统一的数据、算子、执行和通信契约；实现层提供 CPU、CUDA 等设备后端以及第三方 Kernel 和数值库适配；基础设施层提供 MPI 通信运行时、硬件环境、构建部署和测试保障

理想架构用于表达各模块的职责边界，实际实施采用独立路线接入 SGSim：通过 `DBManager` 获取输入数据，在新内核中完成有限元计算，同时保留 SGSim 原有 CPU/MPI 流程及其调用链。新内核 CPU 后端与 SGSim 原有 CPU 流程是两条独立路线；后端选择只作用于新内核，不将 SGSim 原有流程直接改造成新框架的 CPU 后端。

新内核在接口层设计支持 `matrix-free`、受控显式组装和部分组装等计算路径。`matrix-free` 通过统一的 `Operator::apply(x,y)` 接口表达算子作用，作为后续重点研发与验证方向；显式或部分组装路径继续作为 CPU 参考、结果校核、预条件子构造、特定问题求解和必要的回退路径。

`matrix-free` 在适用场景下可根据单元数据、材料参数、几何信息和局部自由度，在线计算刚度算子对向量的作用 `y=Kx`，减少对完整全局刚度矩阵组装和存储的依赖。但该路径不作为所有单元、约束和求解问题的统一默认实现。首期拟选择具有代表性的同构单元和相对明确的约束组合开展原型验证，并与显式装配参考结果进行对照。对于 BDDC 等需要局部子域矩阵、局部—全局映射、接口信息和粗空间数据的预条件子，通过独立的局部或显式辅助数据路径提供相关信息。

是否将 `matrix-free` 扩展到复杂约束、更多单元类型、大规模多 rank、多 GPU 和多节点场景，依据后续正确性、收敛性、内存占用、通信开销和端到端性能测试结果确定。

新路线按以下顺序实施：

1. **数据接入与对象建立。** 读取 `DBManager` 中的网格、材料、载荷、边界、自由度、约束和分区记录，完成全局/局部索引映射、结构校验和连续数据组织，构建 `DistributedMesh`、函数空间和 `DofMap`，明确数据所有权、`owned/ghost` 关系和邻居关系。针对批量局部计算和潜在的 `matrix-free` 算子路径，按照单元类型、材料模型、积分规则、数据类型和约束特征对输入数据进行分组，准备单元批数据、局部自由度索引、几何参数、材料参数、积分数据、边界/约束映射及共享自由度归约所需的信息。数据接入层负责数据读取、索引转换和对象组织，不在算子执行阶段直接依赖数据库内部对象。结果组织和导出接口单独定义，不预设必须回写 `DBManager`。
2. **有限元内核与算子抽象。** 根据网格、函数空间、自由度映射、材料、边界条件和积分规则构建有限元算子。求解器通过统一的 `Operator::apply(x,y)` 接口调用算子作用。在适用的算例和单元组合中，`matrix-free` 算子可按照以下过程执行：
   1. 根据 `Ownership/Halo` 规则更新输入向量中的 `ghost` 数据；
   2. 根据局部自由度映射提取单元或单元批次对应的局部向量；
   3. 完成几何映射、材料计算、数值积分和局部有限元计算；
   4. 在线计算局部刚度算子对输入向量的作用；
   5. 将局部贡献累加到输出向量；
   6. 对共享自由度执行归约，并返回分布式输出向量。

   新内核保留以下互补的计算路径：

   - `matrix-free` 路径：按单元或单元批次计算算子作用，减少完整全局矩阵的组装和存储；
   - 显式或部分组装路径：形成局部矩阵、局部块或受控的全局稀疏矩阵，用于参考校核、预条件子构造、调试、特定求解器适配和回退执行。

   约束处理按照具体问题统一定义，确保算子作用、右端项、边界条件和结果恢复采用一致的约束口径。首期可优先从 `SPC` 等相对明确的约束组合开始验证；`MPC`、`RBE` 等复杂约束通过独立适配或显式回退路径逐步评估，不预设其已经纳入 `matrix-free` 的完整支持范围。

   预条件子通过独立接口接入。可采用 `KSP + CG + Jacobi` 作为基础参考配置，验证算子作用、结果一致性和基本收敛性；在具备相应分区和结构数据的条件下，再评估 `KSP + CG + BDDC` 等结构感知预条件子的适配性。BDDC 所需的局部子域矩阵、局部—全局映射、接口信息和粗空间数据通过独立辅助路径提供，不要求每次 `matrix-free` 算子作用都重新构造完整的全局矩阵。

   根据数据规模、算子重算成本和设备内存条件，评估在线重算、部分组装、积分点缓存、`LocalBlock` 或 `ElementCache` 等策略。`sum factorization` 仅在适用的张量积单元中评估，不作为所有单元的统一实现方式。
3. **张量与执行抽象。** 使用 `LocalTensor`、分布式向量/张量和张量描述符表达单元批数据、局部自由度索引、几何与材料参数、积分点数据、约束映射及算子中间结果，统一描述数据类型、布局、设备位置和所有权。

   `Operator::apply` 作为计算执行的基本接口，由 `ExecutionContext` 组织后端选择、Kernel 派发、事件同步、错误处理和执行资源管理。`Memory/Cache Manager` 负责主机与设备数据的驻留、迁移、缓存和内存预算。对于高频调用的算子，应根据数据访问频率、设备显存容量和传输开销，评估单元数据、材料数据、积分点数据和输入向量是否适合常驻设备或进行缓存复用。具体数据布局和缓存策略以原型验证及分阶段性能测试结果为依据。
4. **设备后端实现。** 新内核 CPU 作为参考执行后端，NVIDIA CUDA 作为首个 GPU 后端。CPU 和 CUDA 后端共享统一的算子、张量、数据布局和执行契约。首先在 CPU 后端完成限定范围内的算子计算闭环，并与显式组装参考路径进行结果对照；随后根据验证结果，评估将已验证的局部算子和批量计算路径迁移到 CUDA 后端的可行性，重点观察 Kernel 执行、设备内存管理、数据传输和同步机制。用户在启动时选择后端和设备，能力查询检查算子、单元、数据类型、数据布局和约束组合是否受支持。对于尚未实现或尚未验证的组合，在执行前给出明确诊断。CPU 后端面向 X86/ARM，OpenMP、线程池等作为内部并行实现方式。其他 GPU 或加速器可通过 HIP、SYCL 或厂商接口按需评估；第三方 Kernel 和数值库通过适配器按算子及后端接入，不固定某个库作为全部计算的统一实现。
5. **分布式通信。** 分布式网格、自由度及向量/张量对象通过 `Ownership/Halo` 定义所有权、`ghost`、邻居关系和数据交换规则。对于分布式算子作用，原则上按照以下顺序组织通信和计算：
   1. 根据输入向量的所有权和邻居关系执行 `halo` 交换；
   2. 各 rank 执行本地单元或单元批次的局部计算；
   3. 将局部贡献写入本地输出；
   4. 对共享自由度执行贡献归约；
   5. 根据求解器需要执行全局归约和同步。

   MPI 通信适配器负责 `halo` 交换、共享自由度贡献归约、全局集合通信和必要的同步；MPI 不负责网格分区、数据所有权确定或局部 Kernel 执行。网格分区和任务划分由独立的分区模块负责，分区结果需要同时服务于局部计算、预条件子构造、通信和负载均衡。期可先采用主机缓冲通信，逐步评估多 rank、多 GPU 和多节点执行。GPU 直接通信、通信计算重叠和拓扑感知优化，根据实际 MPI 能力、硬件拓扑和性能测试结果决定是否启用。
6. **结果验证与集成。** 按全局 ID、自由度编号和物理量约定组织并导出新路线结果，与 SGSim 原有 CPU 结果逐项对照。首期验证重点包括：
   - `matrix-free` 算子作用结果与对应显式矩阵乘法结果的对照；
   - 位移、反力和应力结果与参考路径的对照；
   - 线性求解残差、迭代次数、预条件子构造时间和求解收敛状态；
   - CPU 与 CUDA 路径之间的数值一致性；
   - 多 rank 路径中的 `halo` 交换、共享自由度贡献归约和结果一致性；
   - 数据准备、索引转换、主机与设备传输、局部算子计算、局部矩阵构造、归约和通信等阶段的分项耗时；
   - 不同算子路径在内存占用、通信量、迭代次数和端到端时间方面的对比。

   与现有结果管理流程的衔接方式须经接口和数据结构确认，不预设结果必须回写 `DBManager`。性能结论应在相同算例、相同硬件、相同编译配置、相同进程数和相同收敛标准下比较，不能只依据单个 Kernel 的耗时判断整体收益。首期结论仅适用于已经验证的单元、约束、算例、硬件和软件配置。是否将 `matrix-free` 扩展到复杂约束、BDDC、大规模多 GPU 和多节点场景，应以后续正确性、收敛性、内存、通信和端到端性能测试结果为依据。

#### 2.2.2.3 预期成果

**性能基线与求解器能力**

1. 建立统一、可复现的性能基线，重点统计单元计算、约束处理、矩阵装配、线性求解、通信和结果恢复等环节的耗时、内存和通信开销，明确不同算例的主要瓶颈。结合网格分区测试结果，进一步统计单元数、自由度数、约束关系、接口规模、owned/ghost 数据量和各 rank 负载，分析分区策略对装配和求解性能的影响。
2. 完善第三方求解器的统一接入和配置管理，形成可切换的求解器清单，记录不同求解器的适用算例、编译依赖、运行配置、正确性和性能表现。重点梳理直接法、迭代法以及 PETSc、HYPRE、MUMPS、CPardiso 等求解路径之间的适用关系。
3. 在固定算例、硬件、软件环境、进程配置和收敛标准下，对比矩阵装配速度、线性求解速度、内存占用和端到端性能。力争在典型算例中改善矩阵装配、负载分布和整体求解效率；具体改善幅度以实测结果为准，不预设统一加速倍数。

**迭代法与预条件子**

1. 完善 PETSc、HYPRE 等迭代求解器的接入和配置，比较不同 Krylov 方法及 Jacobi、ASM、ICC、AMG、BDDC 等预条件子的适用性，力争提升典型算例的收敛稳定性，并减少迭代次数和求解时间。
2. 针对 BDDC 等结构感知预条件子，形成全局矩阵、局部子域矩阵、局部—全局自由度映射、接口信息、约束关系和粗空间数据的准备方案，明确其与网格分区、MPI 数据分布和代数求解器接口之间的关系。结合网格分区方案，评估约束关系、接口规模和局部负载对 BDDC 预条件质量和求解效率的影响。
3. 将 `matrix-free` 作为重点验证路线之一，在限定单元、约束和算例范围内验证算子作用、求解收敛和结果一致性；在数据规模和硬件条件适合时，力争降低全局矩阵存储需求并改善局部算子计算效率。显式或局部矩阵路径继续作为参考、BDDC 预条件子构造、结果校核和回退路径。

**多后端异构并行**

1. 形成多后端异构并行实施方案，完成数据适配、张量对象、算子接口、执行上下文、内存管理、设备选择和 MPI 通信边界设计。重点明确单元计算、矩阵/算子作用、约束处理、分区数据和通信归约之间的衔接方式。
2. 完成 CPU 参考路径和 NVIDIA CUDA 后端的原型验证，并根据实际硬件、编译环境和测试条件，评估国产 GPU 及其他 GPU 后端的接入可行性，逐步形成已验证后端清单。对于尚未具备实际硬件和软件条件的后端，仅形成接口适配方案和验证计划。
3. 在单 GPU、多 GPU、多 rank 和具备条件的多节点环境下，验证 CPU/GPU 结果一致性、数据传输、GPU 内存、局部算子计算、通信归约和端到端性能。在单元类型较统一、批量规模足够、分区较均衡且通信开销不过度占主导时，力争实现相对于 CPU 参考路径的明显性能改善。

| **系统工程风险** | 新框架需同时管理有限元对象、算子接口、数据所有权、主机/设备内存、异步执行、MPI 通信和后端能力。接口边界不清、数据生命周期或同步规则不一致，可能造成错误结果、资源泄漏、通信阻塞及性能退化；过度抽象或对某个后端的隐性依赖也会增加维护成本，使原型难以演进为稳定、可扩展的系统。 | 明确四层职责及数据、算子、执行和通信契约，先以 CPU/CUDA 最小端到端原型验证接口，再依据真实扩展需求完善抽象。建立接口版本与兼容规则、模块责任、分层测试、持续集成、资源与错误诊断机制；覆盖单 rank、多 rank、CPU、GPU 及无 CUDA 环境。保持 SGSim 原有路线独立，GPU 依赖可选；新增后端先验证能力与接口兼容。以回归稳定性、故障定位能力和模块变更影响评估工程化成熟度，不以 Demo 可运行替代交付验收。 |
